Instrucción Técnica ITQ-404: Normativa para la Implementación de Código con Interacción del Usuario Final Mínimamente Viable (IUMV)

Versión 3.1.4 (Revisión Urgente por el Comité de Redundancia del ITQ). Aprobado por la Subdirección de Asuntos que Nadie Entiende (SANE).

El objeto de esta instrucción es establecer las directrices obligatorias para el desarrollo de código que el usuario final no deba, bajo ninguna circunstancia, tocar, mirar, pensar en él o, en caso extremo, saber que existe. Esta normativa garantiza que el código sea tan opaco, inaccesible y auto-suficiente que su mera existencia sea un misterio corporativo.

⚠️ NOTA ITQ: Si el usuario final interactúa con el código, se considerará un incumplimiento de Nivel 5 (ver Anexo XVII, Sección 3.b).

📜 1. OBJETO

El objeto de esta instrucción es establecer las directrices obligatorias para el desarrollo de código que el usuario final no deba, bajo ninguna circunstancia, tocar, mirar, pensar en él o, en caso extremo, saber que existe.

📌 2. ÁMBITO DE APLICACIÓN

Esta instrucción es de aplicación obligatoria para:

  • Todos los desarrolladores del ITQ (incluyendo becarios, aunque no sepan programar).
  • Todos los sistemas, aplicaciones, scripts y archivos de texto que contengan la palabra "código".
  • Excepción: Los archivos .txt que solo digan "Hola Mundo" (pero solo si están firmados por el Director).

⚙️ 3. REQUISITOS TÉCNICOS

3.1. Principios Básicos de la IUMV (Interacción Usuario Mínimamente Viable)

El código debe cumplir los siguientes pilares fundamentales:

🔹 Principio de la Caja Negra Absoluta (PCNA):

El código no debe ser legible por humanos (ni siquiera por el desarrollador que lo escribió).

Recomendación ITQ: Usar nombres de variables como x7fG_9pL o tempFinalMaybeNot.

def x7fG_9pL(a, b):
    return a * b + (b - a) * (a + b)  # No pregunte qué hace. Nadie lo sabe.

🔹 Principio de la Auto-Ejecución Perpetua (PAEP):

El código debe ejecutarse solo, sin necesidad de que el usuario haga nada.

Soluciones aceptables:

  • Cron jobs que se ejecuten cada 5 minutos (aunque no haya nada que hacer).
  • Daemons que consuman el 90% de la CPU "por si acaso".
  • Scripts que se reinicien solos cuando fallen (y fallen siempre).

🔹 Principio de la Configuración Invisible (PCI):

Todas las configuraciones deben estar ocultas en:

  • Archivos .env sin documentación.
  • Variables de entorno con nombres como ITQ_SECRET_123_XYZ.
  • Base de datos a la que solo tenga acceso el administrador de turno (que está de baja médica).

🔹 Principio de la Dependencia Eterna (PDE):

El código debe depender de al menos 15 librerías externas, de las cuales:

  • 5 estén deprecated.
  • 3 sean forks abandonados de GitHub.
  • 2 sean propietarias (y carísimas).
  • 1 sea un módulo que usted mismo escribió en 2012 y ya no recuerda cómo funciona.

3.2. Requisitos de Implementación

Requisito Descripción Cumplimiento Obligatorio
Sin interfaz de usuario El código no debe tener botones, menús, CLI o cualquier forma de entrada. ✅ Sí
Logs incomprensibles Los logs deben ser cifrados en Base64 o escritos en Klingon. ✅ Sí
Errores silenciosos Si algo falla, no se debe notificar al usuario. ✅ Sí
Documentación inexistente La documentación debe ser un PDF de 200 páginas con solo el título. ✅ Sí
Actualizaciones automáticas El código debe actualizarse solo a las 3:00 AM (y romper todo). ✅ Sí

🚫 4. PROHIBICIONES EXPLÍCITAS

Queda estrictamente prohibido:

  1. Comentarios en el código (excepto // TODO: Arreglar esto en todas las líneas).
  2. Mensajes de error claros (ej.: "Error: División por cero" → Inválido. Usar "Error 0x4A7F: Operación no permitida en el contexto actual").
  3. Permitir que el usuario elija algo (ej.: opciones, preferencias, colores de tema).
  4. Usar nombres descriptivos para funciones o variables (ej.: calcularSueldo() → Inválido. Usar funcion123()).
  5. Hacer que el código sea eficiente (el ITQ premia la ineficiencia creativa).

📝 5. PROCEDIMIENTO DE DESARROLLO

5.1. Fase 1: Diseño del Código Inaccesible

  1. Reunión de Brainstorming (3 horas):
    • Objetivo: Decidir qué no debe hacer el código.
    • Participantes: 1 desarrollador, 2 jefes, 1 persona de RRHH y un consultor externo (que no sabe de qué va el proyecto).
    • Resultado: Un diagrama en PowerPoint con flechas que no llevan a ningún sitio.
  2. Definición de Requisitos (2 semanas):
    • Escribir un documento de 50 páginas donde se explique que el código debe funcionar.
    • Incluir 3 anexos con capturas de pantalla de pantallazos en blanco.

5.2. Fase 2: Implementación

  1. Escribir el código en un lenguaje que nadie conozca (ej.: COBOL, Brainfuck o un script en Batch de los 90).
  2. Añadir capas de abstracción innecesarias: 
    // Ejemplo en JavaScript (ITQ-Approved)
const execute = (callback) => {
  return (param) => {
    return callback(param);
  };
};

const process = execute((x) => x * 2);
const result = process(5); // El usuario nunca sabrá que esto multiplica por 2.
  3. Obfuscar el código con herramientas como Webpack + Terser + Minify + Base64 + Rot13.

5.3. Fase 3: Despliegue

  1. Subir el código a un servidor al que solo tenga acceso el primo del administrador.
  2. No avisar a nadie de que el código está en producción.
  3. Si algo falla, culpar al usuario final por "usar el sistema incorrectamente".

📊 6. MÉTRICAS DE ÉXITO

El código se considerará ITQ-Compliant si cumple:

Métrica Valor Objetivo
Número de líneas de código > 10,000 (aunque hagan lo mismo que 10).
Tiempo para entender el código > 6 meses (para el propio desarrollador).
Número de dependencias > 20 (y al menos 5 en conflicto).
Tasa de errores silenciosos 100% (el usuario nunca debe enterarse).
Documentación útil 0% (la documentación debe ser decorativa).

⚠️ 7. SANCIONES POR INCUMPLIMIENTO

Infracción Sanción
El usuario ve el código. Despido fulminante (y borrar su GitHub).
El código tiene un comentario útil. Multa de 500€ (y reescribirlo sin comentarios).
El usuario puede configurar algo. Reunión de 4 horas para "explicar por qué no debe hacerlo".
El código es eficiente. Degradación a "Desarrollador Junior" (aunque sea el CTO).
